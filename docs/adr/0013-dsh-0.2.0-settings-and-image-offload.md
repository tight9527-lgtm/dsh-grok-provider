# ADR-0013: Harness 0.2.0 settings ownership and host-owned image offload

- Status: Accepted for dsh-grok-provider 2.0.1
- Baseline: dsh-grok-provider 1.0.6, commit 6cf2bb2

The desktop runtime upgraded to DeepSeek Harness 0.2.0-rc.2, which removed three
APIs this plugin used. `@deepseek-ai/dsh-llm` no longer exports
`offloadRequestImagesWithPolicy`, so the Host entry failed at ESM link time
(`The requested module '@deepseek-ai/dsh-llm' does not provide an export named
'offloadRequestImagesWithPolicy'`) and the plugin could not load at all.
`@deepseek-ai/dsh-settings` no longer exposes `ctx.settings.installSection`, so
per-plugin namespace registration is gone. The browser runtime replaced the
per-plugin `settingsScope` service with the settings domain's shared
`configForms` service.

`2.0.1` therefore supports the `0.2.0` line only, and:

- Settings follow Harness 0.2.0 entry ownership. The namespace IS the Loader
  entry id (`llm-grok`), the form projects from this package's `Config`, and a
  field is editable only when it is declared `.volatile()`. Both Search switches
  are volatile and are read through their cosmokit live reference at call time
  instead of being captured at apply time, which is also how Harness 0.2.0's own
  plugins read live configuration. The plugin registers no section; it declares
  `ctx.settings.configure({ auto: false }, ctx.fiber)` because the browser page
  ships in this package.
- Images follow the Harness 0.2.0 host-decision protocol. The route declares a
  base64-represented occurrence and byte budget derived from the catalog policy
  and from the same `16 MiB` serialized ceiling the encoder enforces. Exceeding
  it throws `ImageOffloadRequiredError`, which maps to a `LlmError` with code
  `IMAGE_OFFLOAD_REQUIRED` and the `offloadImages` count, so
  `dsh-compaction-image-offload` records the durable `image/offload` decision
  before the Harness retries. The adapter never drops a retained image itself.
  Occurrences the Host marked `offloaded` are sent as `offloadedImageText`
  placeholders, and that mark now survives both capture layers (the encoder's
  message capture and the image snapshot). The occurrence limit is decided
  before any attachment byte is read, so an occurrence-only overflow costs no
  reads.
- The browser page reads and writes through
  `ctx.configForms.get("llm-grok")`, keeping the ready/writable/read-only
  fail-closed semantics, the serialized write guard, and effect-owned disposal.
  `dsh.client.inject` gains `@deepseek-ai/dsh-client-ui-slots`, which provides
  the `slots` service the page already injects.

Peers move to `^0.2.0-rc.1 || ^0.2.0-rc.2` with Cordis `^4.0.4` and Schemastery
`^3.18.4`. Harness `0.1.x` is no longer supported: `1.0.x` cannot load on
`0.2.0`, so downgrading is not an alternative for a host that has upgraded.

Two parity limits are deliberate:

- Harness `requiredImageOffload` and `dsh-compaction-image-offload` walk only
  top-level content occurrences, so this plugin counts the same way. After that
  host-compatible decision the compiler verifies the recursive total, including
  images nested one level inside a tool result, against the same occurrence and
  represented-byte budget. A request the Host could never repair is refused with
  the existing invalid-request mapping instead of being sent oversized, and the
  plugin never asks for an offload the Host cannot perform.
- The adapter no longer self-offloads. A request over budget ends that attempt
  with the protocol failure and leaves the durable decision to the Host.

## Local verification, 2026-10-13

- Windows x64, Node `24.21.0`, desktop-bundled DSH `0.2.0-rc.2`
  (`resources/runtime/primary-runtime/runtime.json`: `desktopVersion
  0.2.0-rc.2`, node `24.21.0`), fresh `npm install` of the 0.2.0-rc.2 peer set
  (55 packages, lockfile regenerated).
- Before the port, importing `dist/host/index.mjs` against the installed 0.2.0
  package tree failed with the ESM link error quoted above. After the port the
  same import reports `name`, `inject`, and both Config fields with
  `meta.volatile === true`.
- `npm test`: 284 tests, 282 passed, 2 skipped, 0 failed. The two skips are the
  pre-existing platform-specific checks; the baseline on 0.1.5-rc.2 was the
  283/281/0/2 shape of the same suite.
- The Host suite loads the plugin into the real 0.2.0 `LlmRuntime`, asserts the
  `configure({ auto: false })` presentation claim and its release on unload, and
  drives the Search policy across a configuration reload while a prepared call
  keeps its captured snapshot.
- The compiler regressions cover occurrence-only refusal before reads,
  aggregate-byte refusal after bounded reads, the retried request that sends
  placeholders for exactly the offloaded occurrences, the serialized ceiling,
  and a nested-only overflow that the Host cannot repair.
- The desktop profile on this machine was switched to this build: the locally
  packed `dsh-grok-provider-2.0.1.tgz` (84 files, 298,909 bytes) replaced the
  GitHub-hosted `1.0.6` dependency, and `dsh-grok-provider` was added to
  `dsh.profile.bundles` so its patch layer is composed. After installation the
  four key files are byte-identical to this repository's artifacts and all 14
  profile dependencies resolve. Composing an equivalent profile copy with the
  standalone dsh `0.2.0-rc.2` shows `# == dsh-grok-provider` and `id: llm-grok`
  in the tree. After the desktop restarted, the Host plugin and the settings page
  mount.
- Additional live check, same day: the account dashboard then reported an
  unavailable model catalog and quota. The cause was environmental, not a port
  regression: the three upstream calls (`/v1/models`, `/v1/billing`,
  `/v1/responses`) use the host process's `fetch`, and Node's `fetch` does not
  read the Windows system proxy (Clash on `127.0.0.1:7897`); this machine sets
  only `NO_PROXY` and `NODE_USE_ENV_PROXY=1` globally, so the proxy URL existed
  solely in a `dsh web` launcher script. A direct `fetch` failed with
  `UND_ERR_CONNECT_TIMEOUT`, the same call with
  `HTTPS_PROXY=http://127.0.0.1:7897` returned `401` (reached, unauthenticated),
  and installing the dispatcher the way the DSH launcher does produced the same
  `401` without relying on `NODE_USE_ENV_PROXY`. With the proxy in place the
  complete dashboard path returned `models.state=ready` (4 models) and
  `quota.state=ready` (weekly, with a percentage), both endpoints answering 200.
  The plugin deliberately does not resolve the system proxy itself: the Harness
  launcher owns undici's global dispatcher, so the provider keeps using
  `globalThis.fetch`. The fix is a launch environment carrying `HTTPS_PROXY` /
  `HTTP_PROXY`; both READMEs now document the symptom and the check.
- Not verified: no live `/v1/responses` conversation was sent on `0.2.0`, no
  Windows real-device browser sign-in, and no publication.
